## App Router 네비게이팅
### 기본 동작
- 페이지 라우터와 마찬가지로 클라이언트 사이드 렌더링(CSR)으로 페이지 이동 처리
- 초기 접속 시 사전 렌더링 -> 이후 페이지 이동 시 필요한 JS 번들을 받아와 브라우저에서 실행

### 프리페칭
- 페이지 이동 전에 미리 필요한 데이터를 받아와 속도 최적화

### 차이점
- App Router: 페이지 이동/프리페칭 시 JS 번들 + RSC Payload (서버 컴포넌트 실행 결과물) 모두 전달
- JS 번들에는 클라이언트 컴포넌트만 포함 -> 서버 컴포넌트 데이터는 누락되므로 RSC Payload 필요

### 정리
- CSR 방식 유지: JS 번들과 RSC Payload를 함께 받아옴
- 브라우저는 JS 번들을 실행하고 RSC Payload와 합쳐 페이지 교체

## App Router 데이터 페칭
### Page Router
- 모든 컴포넌트가 클라이언트 컴포넌트
- 데이터 페칭은 서버 전용 함수에서만 가능
  - getServerSidProps (SSR)
  - getStaticProps/getStaticPaths (SSG/ISR)
- 데이터는 페이지 컴포넌트에만 props로 전달 -> 하위 컴포넌트에는 props/context로 전달

### App Router
- 서버 컴포넌트 도입으로 구조 변화
- 서버 컴포넌트는 브라우저에서 실행되지 않음 -> async 함수로 선언 가능
- 컴포넌트 내부에서 await fetch() 직접 실행해도 문제 없음
- 특수 함수(getServerSidProps 등) 불필요
- 데이터가 필요한 각 컴포넌트 내부에서 직접 fetch 가능 (권장 방식)

## 데이터 캐시
### 데이터 캐시
- fetch()로 불러온 데이터를 Next.js 서버 측에서 캐싱
- 장점
  - 불필요한 요청 방지 -> 성능 최적화
  - 특정 시간/조건에 따라 자동 갱신 가능
- 반드시 Next.js의 fetch 사용 (Axios 등 미지원)

### 데이터 캐시 옵션
- cache: 'no-store'
  - 캐싱 x, 매 요청 시 백엔드 서버에 새로 요청
  - 항상 최신 데이터가 필요할 때 사용
- cache: 'force-cache'
  - 한 번 불러온 데이터를 영구 캐싱
  - 이후 요청은 캐시된 데이터만 사용 (백엔드 호출 없음)
- next: { revalidate: n }
  - ISR과 유사
  - 최초 요청 -> 데이터 캐싱 -> 이후 요청 시 캐시 데이터 사용
  - n초 후 요청이 들어오면:
    - 캐시 데이터 반환 (stale 처리)
    - 동시에 백엔드에서 최신 데이터 다시 불러와 캐시 갱신
- next: { tags: [...] }
  - 특정 요청 시에만 캐시 갱신 (On-demand ISR과 유사)
  - 서버 액션/라우트 핸들러 등과 함께 사용

## 리퀘스트 메모이제이션
### Request Memoization
- 하나의 페이지 렌더링 과정에서 중복된 API 요청을 캐싱하여 한 번만 요청하도록 최적화하는 기능
- 동일 요청이 여러 번 발생해도 첫 요청 결과를 재사용

### 동작 방식
- 첫 요청 발생 -> 캐시에 아무것도 없으므로 백엔드 서버 요청
- 응답 결과를 Request Memoization 캐시에 저장
- 이후 동일 요청 발생 시 -> 캐시된 데이터 재사용, 서버에 재요청 x

### 특징
- 렌더링 과정에서만 유효 -> 페이지 렌더링이 끝나면 캐시는 즉시 소멸
- 목적: 중복된 API 요청 방지
- 데이터 캐시: 영구적 저장 (서버 종료 전까지 유지)
- Request Memoization: 일시적, 렌더링 중에만 유지

## 풀 라우트 캐시
### Full Route Cache
- Next.js App Router에서 제공하는 페이지 캐싱 기능
- 빌드 타임에 페이지를 미리 렌더링 후 저장
- 이후 요청 시 새로 렌더링 없이 캐시된 페이지 그대로 응답

### 동작 원리
- 빌드 타임에 정적 페이지(Static Page) 미리 렌더링
- 결과물을 풀 라우트 캐시에 저장
- 서버 실행 후 해당 페이지 요청이 들어오면 캐시된 HTML 반환 (새 렌더링 x)

### 특징
- SSG와 유사
- 정적 페이지에만 적용 (Dynamic Page 제외)
- ISR처럼 Revalidate 옵션 사용 가능

### 페이지 분류
- Dynamic Page
  - 다음 조건 중 하나라도 해당하면 Dynamic Page
  - fetch 시 캐시 옵션 없음 또는 cache: 'no-store'
  - 동적 함수 사용 (쿠키, 헤더, 쿼리스트링 등)
- Static Page
  - 동적 함수 x
  - fetch 시 캐싱 옵션 사용
  - 캐싱 가능하므로 풀 라우트 캐시 적용됨
 
## 라우트 세그먼트 옵션
### dynamic
- 데이터 페칭 및 렌더링 모드 제어
- auto (기본): Next.js에서 자동 판단
- force-dynamic: 항상 서버에서 새로 렌더링
- error: 동적 데이터 사용 시 에러 발생
- force-static: 강제로 정적 페이지로

### fetchCache
- fetch 캐싱 전략 제어
- auto (기본)
- default-cache: 기본 캐싱
- only-cache: 캐시만 사용
- force-cache: 무조건 캐시 사용
- default-no-store: 캐싱 안 함
- only-no-store: 무조건 네트워크 요청

### revalidate
- ISR처럼 페이지 재생성 주기 설정
- false: 재생성 없음
- 0: 요청 시마다 재생성
- n: n초마다 갱신

### runtime
- 실행 환경 지정
- nodejs: Node.js 환경
- edge: Edge 런타임

## 클라이언트 라우터 캐시
### Ckient Router Cache
- 브라우저(클라이언트) 측에 저장되는 캐시
- 페이지 이동 시 중복된 레이아웃 데이터를 다시 받아오지 않도록 최적화하는 기능

### 동작 원리
- 사용자가 index 페이지 접속
  - 정적 페이지라면 풀 라우트 캐시에서 불러옴
- search 페이지 이동
  - 동적 페이지이므로 서버에서 새로 생성
  - 이때 RSC Payload(서버 컴포넌트 결과물) 안에는 공통 레이아웃과 해딩 페이지 컴포넌트, 기타 서버 컴포넌트 모두 포함
- 공통 레이아웃 중복 전송 -> 불필요한 데이터 낭비 발생

### 클라이언트 라우터 캐시
- Next.js는 중복 방지를 위해 클라이언트(브라우저)에 전용 캐시 공간 생성
- 서버에서 받은 RSC Payload 중 레이아웃 관련 데이터 추출 -> 캐싱
- 이후 페이지 이동 시
  - 공통 레이아웃: 캐시에서 재사용
  - 개별 페이지/서버 컴포넌트: 서버에서 새로 요청
 
## 스트리밍
### Streaming
- 서버에서 클라이언트로 데이터를 작게 쪼개어 순차적으로 전송하는 기술
- 모든 데이터가 준비되지 않아도 일부 데이터부터 렌더링 가능 -> 빠른 초기 화면 제공

### 동작 원리
- 서버에는 빠르게 렌더링 가능한 컴포넌트 (레이아웃, 단순 UI) 먼저 전송
- 렌더링이 오래 걸리는 컴포넌트는 fallback으로 대체
- 해당 컴포넌트 렌더링이 완료되면 후속 데이터만 추가 전송 -> 클라이언트 화면에서 교체
- 초기 로딩 시간 단축 가능
- 사용자 경험 개선
- 주로 Dynamic Page에 활용

### 페이지 스트리밍
- 전체 페이지 단위
- 페이지 파일 내부에서 Suspense 사용
- 페이지 전체 응답 속도 개선
- 제어 범위가 커서 세밀화 최적화는 어려움

### 컴포넌트 스트리밍
- 특정 컴포넌트 단위
- 특정 UI 블록을 Suspense로 감싸서 개별적으로 스트리밍
- 페이지 일부만 비동기 로딩 가능
- 컴포넌트 단위로 분리해야 해서 설계가 다소 복잡

### 스켈레톤 UI
- loading.tsx 파일을 해당 경로에 생성
- 데이터/컴포넌트 준비 전 스켈레톤 화면 먼저 노출

### 에러 핸들링
- error.tsx 파일을 해당 경로에 생성
- 해당 라우트에서 에러 발생 시 자동 표시
